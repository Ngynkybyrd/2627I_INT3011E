A B S T R A C T
This study represents generalized Sudoku with cell–value Boolean variables and compares pairwise,
sequential-counter, and bitwise At-Most-One encodings using the same Glucose3 solver. The dataset
contains 60 synthetic instances at grid sizes 4, 9, 16, and 25 and three clue densities, plus 20 public 9×9
instances. CP-SAT/HiGHS are evaluated on a 16-instance subset; Gurobi, CPLEX MIP, and CP Optimizer
on a 10-instance subset. Three repetitions and a 10-second cutoff covering model construction/loading and
solving produce 906 runs: 903 independently checked solutions and three HiGHS timeouts on one instance.
All three SAT encodings solve all 80 instances in every repetition. On five synthetic 25×25 instances with
30% clues, median total times for pairwise, sequential, and bitwise are 0.402449, 0.159527, and 0.210650
seconds; build costs exceed solving costs. However, rankings change with grid size; CPLEX MIP has a
lower median than pairwise on four common public instances. These results emphasize construction costs
and comparisons on identical instance sets, without establishing a universally superior solver or encoding.
Uniqueness remains unverified and baseline coverage is limited.

1. Introduction and related work
Sudoku has concise rules, yet the same feasibility problem can be represented in SAT, CP, or ILP . As grid size increases,
representations can differ in variable counts, constraints, and model construction costs. Evaluation therefore needs to distinguish
representation size, construction/loading time, and solving time; fewer clauses alone do not establish faster solving. This work
considers generalized Sudoku with 𝑛 ≥ 2 and 𝑁 = 𝑛 2, focusing on three AMO encodings within a common SAT formulation.
1.1. Related foundations
Lynce–Ouaknine formulate Sudoku using cell–value Boolean variables and distinguish minimal and extended models [11]. Their
work supplies modeling background, not results for this project’s dataset. Sinz presents a sequential unary counter for cardinality
constraints [14]. PySAT supplies a toolkit and the CardEnc API for AMO choices [ 10, 12]. Here, ALO and the four EXO families
stay fixed while AMO varies among pairwise, seqcounter, and bitwise; bitwise AMO is not identified with Sinz’s binary counter.
These sources support construction methods, not correctness checks or measurements of the current program.
1.2. Research questions
1. How do the three AMO encodings affect primary/auxiliary variables, clauses, and build/solve/total times as grid size and clue
density vary?
2. On matching instance sets, how does SAT compare with CP-SAT and HiGHS ILP in valid-solution coverage and time under
the same cutoff?
3. What additional evidence do available Gurobi/CPLEX comparisons on the small subset provide, and how do runtime/license
limits restrict coverage?
S80/B16/C10 specify comparison subsets before measurement. Section 9 answers these questions using checked measurements and
the correct intersections; SAT statistics for all of S80 are not combined with B16/C10 baseline statistics as though they used the
same sample.
1.3. Scope of the contribution
The course-project contribution is an implementation of generalized Sudoku models, integration of established encodings under
a common specification, model/solution validation, and a reproducible evaluation through 906 runs on defined comparison sets. No
new encoding is proposed, existing runtimes/libraries are not presented as algorithms invented by the author, and no superiority is
claimed for all 𝑛 or all Sudoku instances.

Forward direction.Cell ALO and AMO give exactly one value per cell. Row–value, column–value, and block–value groups require
every value exactly once in the corresponding unit. Unit clauses preserve every clue. Decoding a CNF model’s primary variables
therefore yields a valid solution.
Reverse direction. From a Sudoku solution preserving clues, set the selected cell–value variables true. Every group has exactly
one true input. Pairwise is already satisfied; extend sequential groups by prefix ORs and bitwise groups by the true input’s code.
Disjoint auxiliary sets let these local extensions combine into a global satisfying assignment 𝐴. This does not require every auxiliary
assignment to satisfy the CNF, nor imply uniqueness.

7.1. Library use and validation
The SAT backend is pysat.solvers.Glucose3 in python-sat 1.9.dev16 [ 10, 1, 2]. The five baselines use OR-Tools CP-
SAT [4], gurobipy [5], the direct CPLEX Python API (cplex.Cplex, without DOcplex.MP) [8], DOcplex.CP for CP Optimizer [9],
and highspy for HiGHS [ 6, 7]. In these adapters SciPy supplies sparse ILP matrices; it is not a HiGHS solve backend through
scipy.optimize.milp. For SAT, the public API consists ofprepare_backend and solve_sat; each call uses a fresh Glucose3
instance. The adapter calls the CNF builder with the selected encoding, uses interrupt-capable native solving, then passes the model
through decoding and validation.check_solution. Auxiliary variables do not determine decoded cell values.
For comparisons, solve_baseline accepts one of cpsat, gurobi, cplex_mip, cpoptimizer, or highs. CP-SAT/CP
Optimizer use the CP builders; Gurobi/CPLEX MIP/HiGHS consume the same ILP matrix, bounds, integrality, and constant
objective. Each call has fresh objects and one thread/worker. Adapters retain raw statuses and use the same production checker.
MIP decoding accepts only finite values within 10−6 of 0 or 1, with exactly one selected value per cell; arbitrary rounding of
fractional solutions is not allowed. HiGHS must also report acceptable primal feasibility/integrality before decoding. A time-limit
incumbent can become SAT only if it arrived on time and passes checking. UNSAT requires infeasibility evidence; missing runtime,
license limits, and unknown outcomes remain distinct.
7.2. Timing boundary and process safeguards
Imports/input reading precede measurement. Build includes model/CNF construction and solver creation/loading; solving uses
the remaining budget. Decoding, checking, and cleanup are outside build+solve. Deadline admission uses native-solve completion,
not checker completion as the solve endpoint. Timing components unknown after forced termination must remain missing rather
than invented.
SAT native interruption and baseline timers/native limits are cooperative. In DOcplex 2.32.264, TimeLimit is embedded in
transmitted CPO, so an exact post-load native TimeLimit is not promised: the adapter uses preload for build accounting, an
abort_search timer against the actual deadline, and late-result rejection. The private preload hook needs rechecking on DOcplex
upgrades. If timer joining fails, the adapter reports ERROR and may defer native deletion to avoid a callback into released memory.
The measurement-end hook and hard worker/process-tree guard are accepted. The runner uses START/END to apply the cutoff
to measurement, then switches to a postprocessing watchdog and process-tree cleanup as needed. The pilot exercised this integration;
native timeout alone remains cooperative. Section 8 describes the frozen main configuration; Section 9 reports its executed results
separately from the pilot.

8.3. Timing and process safeguards
Worker imports/input reading precede START. START/END use synchronized shared state and a monotonic clock. From
START, the 10-second cutoff includes model/CNF construction, solver creation/loading, and solving; solving uses only the
remaining budget. On-time END switches to a separate postprocessing watchdog. Decoding, validation, cleanup, and CSV/output
I/O are outside build+solve. Missing or late END causes TIMEOUT; unknown timing components remain missing.
The Windows runner assigns the worker to a kill-on-close Job Object before releasing execution, terminates the process tree on
deadline, and waits for descendants. The startup watchdog is 60 seconds before START; postprocessing has 30 seconds after on-time
END. Startup/postprocessing/cleanup failure is ERROR, distinct from measurement timeout. Watchdogs do not extend solve time.
The hard guard and measurement-end hook passed the pilot before use in the 906 fresh main runs.
CP Optimizer uses DOcplex 2.32.264 private preload to charge compile/send/load to build. Native TimeLimit is embedded in
CPO before loading; after loading, cooperative abort_search is backed by the external guard. Exact post-load native TimeLimit
changes are not promised; DOcplex upgrades require rechecking the private hook as in Section 7.
8.4. Aggregation rules
For each instance–configuration pair with three SAT runs, take the three-run median separately for build, solve, and total, then
take the median of per-instance medians within the specified stratum. Components are aggregated independently: per-run total
equals build+solve, with setup included in build, but the two group medians need not sum to the group total median. Paired runtime
comparisons use only IDs with three SAT runs on both sides and report matched counts; solved counts and timeouts cover the full
selected scope. Per-run PAR-2 uses SAT total or2×10 = 20seconds for TIMEOUT; ERROR, INV ALID_INPUT, UNA V AILABLE,
and LICENSE_LIMIT are excluded. The fastest repetition is not selected, and missing timings are not filled with zero.

9.3. Timeouts, PAR-2, and traceability
All three timeouts are the three HiGHS repetitions of synthetic-N25-p30-s0. This ID has no SAT median; the runtime
intersection between HiGHS and SAT/CP-SAT on B16 contains 15 IDs, while its intersection with commercial engines on C10 still
contains 10. T wo SAT encodings share 80 IDs. Each timeout receives PAR-2 = 2 × 10 = 20seconds, for a total timeout penalty of
60 seconds; mean PAR-2 for the HiGHS N25/30% stratum is 20 seconds. Missing timings are not zero: r3 lacks build/solve/total
and remains missing, while r1/r2 have observed totals near the cutoff but remain TIMEOUT. Successful-only runtime statistics
must be read with the counts in Table 3. Tables and figures use the locked final analysis; summary.csv, instances.csv,
matched-pairs.csv, and cnf.csv retain detailed statistics. paper/raw-row-index.csv maps job IDs to original CSV rows;
the audit retains configuration, versions, and hashes. Pilot data are not merged, and the benchmark is not rerun to select favorable
results.
10. Limitations
Synthetic instances originate from structured valid grids and transformations, introducing generator bias rather than representing
all Sudoku. Larger grids or fewer clues do not establish greater diﬀiculty. Public instances are also externally machine-generated,
with only 20 sampled from one hard.txt bucket; bucket names/ratings are uncalibrated source labels. The 80 instances have SAT
evidence but unverified uniqueness; finding one valid completion is not a uniqueness certificate.
Baselines are supplementary small samples: compare three SAT encodings on S80, CP-SAT/HiGHS on B16, and commercial
engines on C10 or the available intersection. Paired runtimes use instances with three successful repetitions in both configurations
and disclose scoped counts/coverage. Medians from different sets are not a common-sample comparison. A 10-second timeout is
cutoff-censored, not true solving time. ERROR, UNA V AILABLE, and LICENSE_LIMIT are distinct from TIMEOUT and excluded
from timeout PAR-2 penalties.
Free editions restrict coverage: Gurobi size-limited allows 2,000 variables/2,000 linear constraints; CPLEX MIP Community
allows 1,000/1,000. The 4 × 4/9 × 9 C10 models fit and completed all three main repetitions on C10; this does not imply all-S80
coverage. CP Optimizer has a model/search-space-dependent limit: a size failure on one 16 × 16or 25 × 25 grid does not establish
failure for every grid of that size. HiGHS is not relabeled as Gurobi/CPLEX.
One machine, one version configuration, three repetitions, and a finite cutoff do not establish generality across hardware/solvers.
B16 has one ID per synthetic stratum; C10 contains only small grids and four common public instances. Millisecond differences are
sensitive to overhead; no statistical significance testing, RAM measurement, or search counters are provided. Baselines use models
and engines different from SAT, so differences cannot all be attributed to encoding. Smoke/pilot are separate integration gates and
are excluded from main results.

11. Conclusion
The cell–value model with four EXO families permits AMO substitution under a common Sudoku specification. Pairwise,
sequential-counter, and bitwise encodings with the same Glucose3 solver solve all 80 instances in all three repetitions. On five
synthetic N25/30% instances, sequential has a median total of 0.159527 seconds versus pairwise’s 0.402449 and bitwise’s 0.210650
seconds; build accounts for most cost in this stratum. This answers the encoding question through variable/clause tradeoffs and
construction/loading cost, not solving alone. Rankings change on small grids, so no universal winning encoding is selected. CP-
SAT/HiGHS on B16 and commercial solvers on C10 provide scoped comparisons: HiGHS times out in all three runs of one ID,
while CPLEX MIP has a lower median than pairwise on four common public instances. These small samples do not establish that
SAT, CP, or ILP always wins. Future work should broaden instance sources, verify uniqueness and diﬀiculty, increase repetitions
and machines, and examine runtime costs further while retaining matched subsets and cutoff-aware treatment.
